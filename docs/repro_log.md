# 汶川地震泥石流数据集复现日志

这篇记录我复现一篇数据论文的整个过程, 从拿到原始数据, 到跑出结果, 到写成报告.
尽量写得直白, 能看懂就能复现, 也方便以后自己回头看.

> 复现对象: Wang L, Chang M, Le J, Xiang L, Ni Z. (2022)
> *Two multi-temporal datasets to track debris flow after the 2008 Wenchuan earthquake*
> Scientific Data 9:525, 数据在 Zenodo (doi:10.5281/zenodo.6891244)

## 0 这次要干什么

一句话: 把 2008 年汶川地震之后, 龙门山一带发生的 186 次泥石流, 和对应的降雨数据,
整理成能建模的表, 然后做两件事:

- 任务 A: 根据一场雨的特征, 判断它会不会引发泥石流 (降雨阈值)
- 任务 B: 根据一个流域的地形和防治信息, 判断它容不容易发泥石流 (易发性)

论文本身是"数据论文", 只给数据, 不给建模结果. 所以模型和阈值都是我自己做的,
不是抄论文的. 论文的作用是告诉我这些数据长什么样.

## 1 准备阶段

### 1.1 拿到数据

数据是 Zenodo 上打包好的, 一共几个压缩包和 PDF 说明文件. 放到 `data/raw/` 下.
内容大概分两套:

- 数据集 1: 186 条泥石流事件表 + 79 个流域多边形 + 465 个逐小时降雨序列
- 数据集 2: 拦砂坝信息 (哪个流域建了坝, 建成年份, 有没有成功防治)

我把压缩包解压后, 目录结构长这样:

```
data/raw/
├─ dataset1/Dataset1 Debris flow and Triggering rain/
│  ├─ Dataset1_Debris flow.csv
│  ├─ Debris_flow_catchment.{shp,dbf,prj}
│  └─ ID_RG_DF_DATA/ID_RG_DF_<DF_ID>/*.txt
├─ dataset2/Dataset2 Dam/Dataset2_Dam.csv
├─ Read me.pdf
└─ References of data sources.pdf
```

### 1.2 环境

Windows 11, Python 3.12, 用的库都是传统机器学习的, 没有深度学习:

```text
pandas, numpy, scikit-learn, matplotlib, seaborn, xgboost(可选)
```

固定了随机种子 `20220901`, 这样每次跑出来都一样, 可以复现.

## 2 读数据时踩的坑

这步最折磨人, 也最关键. 数据本身有几处"坑", 不处理后面全乱.

### 2.1 坐标列反了

打开事件表 `Dataset1_Debris flow.csv`, 发现 `Latitude` 那一列存的是 103.x,
`Longitude` 存的是 31.x. 但汶川在四川, 纬度 31, 经度 103. 也就是说
**两列名字和内容对调了**.

我要是直接拿它做空间归属, 所有点都会跑到地球另一边去.
处理办法: 读进来的时候把两列名字换回真值 `lon` / `lat`, 原始的列留着备查.

### 2.2 一半事件没有时刻

186 条事件里, 95 条没有精确发生时刻 (`Time(24 hour)` 是空的).
怎么办? 就用当天的 00:00 顶一下, 然后标注 `time_missing=True`.
因为时刻不准, 我判断"这场雨是不是触发了泥石流", 就用**整个日历日**当窗口,
而不是精确到小时. 代价是少数字会被记歪, 但比瞎猜强.

### 2.3 事件名和流域名对不上

事件表里一个事件就是一个沟名, 比如 `Mayangdian`. 但流域表里一个流域可能是
好几个沟用 `/` 连起来, 比如 `Douyaping/Mayangdian/Maliuwan/Qingling/Guanshan`.

所以先做"名字最长匹配", 匹配不上的再用"点在多边形里"的空间判断兜底.
最后 186 个事件里有 167 个 (89.8%) 找到了自己的流域.

## 3 洗数据: 把原始表变成能建模的表

### 3.1 降雨怎么切成一 场场雨

每个事件文件夹里, 是周围雨量站从"事件前 7 天到事件后 1 天"的逐小时降雨.
这段时间里不可能只有一场雨, 得切成很多场, 才能既有正样本又有负样本.

切分规则 (都写成常量, 好调):

| 常量 | 值 | 意思 |
|---|---|---|
| 湿小时阈值 | 0.1 mm | 这个小时下雨了才算湿 |
| 干间隔 | 6 h | 连续 6 小时不下雨, 就切成两场 |
| 最小总雨量 | 1.0 mm | 总雨量不到 1mm 的场次丢掉 |
| API 衰减 | 0.9 | 前期降雨指数, 越久远权重越小 |

切完以后, 每场雨算 16 个特征, 比如总雨量, 历时, 最大单小时雨量,
最大 24 小时雨量, 前期雨量, 前期降水指数 API 等等.

### 3.2 标标签

一场雨和泥石流当天"重叠"的, 标成正样本(触发). 同一窗口里其它雨, 就是负样本.
这样负样本是数据自带的, 不用我造假的.

最后得到 **1597 行**, 其中正样本 **444 个**, 负样本 **1153 个**.

## 4 流域特征: 从多边形算出地形指标

流域是一个个多边形, 我用自己手写的 SHP 读取器把它们读进来 (不想装 geopandas,
怕复现时卡在装二进制库上). 从多边形能算出:

- 面积, 周长, 形状紧凑度
- 包围盒的长宽
- 流域质心的经纬度
- 支沟个数

加上数据集 2 的防治信息: 坝的数量, 建成年, 有没有坝.

> 没有高程数据(DEM), 所以**不虚构坡度**这种特征, 缺就是缺.

## 5 任务 A: 降雨阈值分类

### 5.1 问题来了: 行和行不独立

一次泥石流事件贡献好几个雨量站的雨, 同一场雨在好几个站上都算一遍.
如果随机切训练测试, 同一场雨可能一半在训练一半在测试, 就是**泄漏**,
结果虚高.

所以我同时报三种切法, 把虚高量出来:

| 切法 | 怎么切 | 作用 |
|---|---|---|
| random | 分层随机 7:3 | 有泄漏, 只看虚高上界 |
| group_event | 按事件分组(GroupKFold) | 主协议, 同事件不跨折 |
| temporal | 用 2013 年前训练, 2016 年后测试 | 看能不能跨时间泛化 |

### 5.2 结果

主协议下, 随机森林最好:

- accuracy 0.9562
- F1 0.9201
- ROC-AUC 0.9832

random 切法只比它高 0.63 个百分点. 说明泄漏有, 但不致命.

特征重要性也很说明问题: 前两名是**湿小时数**和**历时**, 单小时峰值排到第 14.
意思是: 判断会不会触发, 主要看"下了多久, 下了多少", 不是"下得多急".

### 5.3 temporal 协议别当真

2016 年后只有 57 行测试数据, 指标乱跳 (accuracy 0.877~0.983).
57 行撑不起结论, 所以我不采信它. 这也说明: 拿这批数据论证
"阈值随震后恢复"不够.

## 6 经验 I-D 阈值: 跟机器学习比一比

### 6.1 又踩一个坑: 雨历时怎么定义

泥石流阈值常用 `I = a * D^-b`, I 是雨强, D 是历时. 关键是 D 怎么算.

我一开始用"一整场雨"的时长当 D. 结果不行: 龙门山季风雨经常连下几十个小时,
D 被拉得很长, 点数又被少数超长样本带着走, 拟合出来毫无意义 (log-log 相关只有 0.27).

正确做法是**固定窗长**: 对每个 D (1,3,6,12,24,48,72 小时), 看任意 D 小时窗口内
的最大降雨量, I = 最大雨量 / D. 这样每场雨贡献 7 个点, 一共 11179 个点.

### 6.2 拟合结果

一共拟合 6 条曲线, 跟机器学习用**同一批行, 同一批标签**评分.

最重要的发现: **原始点云的 OLS 只有 r2 = 0.35~0.49**, 但先按窗长取分位数再拟合,
r2 能到 0.96~0.99. 意思是幂律只在"包络"上成立, 把所有点直接丢进最小二乘,
会得到一条不靠谱的线. 文献里那些漂亮的幂律, 基本都是分箱取包络出来的.

跟机器学习比, 经验曲线 F1 最高 0.6055, 随机森林 0.9201, 差 0.31.
为什么? 因为经验曲线只用 (I, D) 两个量, 机器学习用了 16 个特征.

### 6.3 有个尝试失败了, 我如实记下

我试过从随机森林的 0.5 概率等高线, 反推一条"ML 等效阈值曲线".
结果返回空, 失败了: 因为合成样本只有一个特征被赋值, 其它 15 个填 0,
概率曲线不单调, 找不到稳定的 0.5 穿越点. 我没硬调参把它"凑"出来,
就把失败过程写进报告了.

## 7 任务 B: 流域易发性分类

79 个流域, 每个一行. 标签是: 事件数 > 中位数 (1) 就是易发, 否则不是.
结果正类 35 个, 负类 44 个.

评测用 RepeatedStratifiedKFold, 5 折 x 10 次, 报均值标准差.

- 逻辑回归 accuracy 0.7598 (std 0.0970), AUC 0.8082
- XGBoost AUC 最高 0.8186

但注意: 模型之间 accuracy 差距 (0.71~0.76) 比标准差还小, 所以
**不能给模型排序**, 只能说形态加防治特征能给 0.78~0.82 的排序能力, 还不稳定.

特征里 `centroid_lat` (纬度) 最重要, 但我不解读成"纬度越高越危险".
它更可能是"离震中多远"的代理变量. 防治特征 (`dam_number` 之类) 重要性都很低.

## 8 坝到底有没有用? 答案: 这批数据看不出来

| 坝数 | 流域数 | 平均事件数 |
|---|---|---|
| 0 | 56 | 1.88 |
| 1 | 9 | 2.78 |
| 2 | 3 | 3.00 |
| >=3 | 11 | 2.55 |

有坝的流域平均事件数 (2.55~3.00) 比无坝 (1.88) 还多. 但这**不是**坝没用,
而是**选址偏差**: 坝恰恰建在灾害多的地方. 佐证是面积和有没有坝相关 0.51,
但面积和事件数几乎不相关 (-0.02).

要真正评估坝的效果, 得做"建坝前后对比" (before/after), 不是横截面比.
这批数据建成年高度集中在 2011~2014, 坝建成后的年份太少, 做不了.

## 9 我怎么保证我的数字是对的

我吃过亏: 报告草稿里几个数字是我自己脑补的, 和实际跑出来对不上.
后来做了个规矩: **报告里所有数字, 都必须来自结果 JSON/CSV, 由脚本自动生成**.
改了分析代码, 就重跑一遍, 再核对一遍.

具体是这两个脚本:

- `scripts/explore/report_numbers.py` 生成 `docs/_numbers.md`
- `scripts/explore/audit_artefacts.py` 生成 `docs/_audit.txt`

## 10 怎么一键复现

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run_all.py
```

`run_all.py` 会顺序跑 5 个阶段, 最后自动做 SHA-256 逐字节校验.
我实际跑过: 两次运行 16 个产物全部 bit-for-bit 一致, 输出:
`OK: every artefact reproduces bit-for-bit.`

## 11 一句话总结

数据论文给数据, 不给答案. 我把它洗干净, 用传统机器学习跑了两个任务,
发现: 降雨能不能触发, 主要看"下得久不久"不是"下得急不急";
经验 I-D 阈值只在分位数包络上好看, 实际预警不如随机森林;
坝的作用, 这批横截面数据看不出来, 因为坝建在本来就危险的地方.
